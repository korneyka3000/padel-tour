## Р-013 · Локальный Postgres в docker для проверки перед пушем

**Дата:** 2026-08-08 · **Веха:** M2

Перед пушем прогонять набор ещё и на локальном Postgres:

```
docker run -d --name padel-pg -e POSTGRES_USER=padel -e POSTGRES_PASSWORD=padel \
  -e POSTGRES_DB=padel_test -p 55432:5432 postgres:18-alpine
TEST_DATABASE_URL='postgresql://padel:padel@localhost:55432/padel_test' uv run pytest
```

**Почему.** Первый же прогон M2 в CI дал 15 падений, невидимых на SQLite: `seed` не влезал
в `INTEGER` (Postgres — знаковый 32-битный, а `randbits(32)` беззнаковый), и пересозданные
записи состава тянулись к имени игрока ленивым запросом, чего асинхронная сессия не умеет
(`MissingGreenlet`). Оба — ровно то, ради чего заведена
[Р-008](#р-008--тесты-идут-на-sqlite-локально-и-на-postgres-в-ci), но ловить их через push
в CI по одному — медленно и неопрятно.

**Почему не Neon.** Пробовал прогнать против облачной базы — каждый тест пересоздаёт схему,
и по сети это уходит в минуты. Локальный контейнер отрабатывает за секунды.

## Р-012 · Все временные метки нормализуются в UTC на уровне типа

**Дата:** 2026-08-08 · **Веха:** M2

Свой `UtcDateTime` вместо `DateTime(timezone=True)`: на запись требует aware-значение и
приводит к UTC, на чтение проставляет UTC, если диалект таймзону потерял.

**Почему.** Нашлось круговым тестом, а не рассуждением: Postgres `timestamptz` возвращает
aware-время, SQLite таймзон не знает вообще и возвращает naive. Одно и то же сравнение
проходило локально и упало бы в CI. Ровно та разница диалектов, ради которой
[Р-008](#р-008--тесты-идут-на-sqlite-локально-и-на-postgres-в-ci) и заведена.

**Чем платим.** Naive-время теперь нельзя записать — будет исключение. Это осознанно:
молча додумывать таймзону хуже, чем упасть.

**Дата:** 2026-08-08 · **Веха:** M2

## Р-009 · Первичные ключи — UUIDv7

**Дата:** 2026-08-08 · **Веха:** M2

`uuid.uuid7()` из стандартной библиотеки Python 3.14.

**Почему.** UUIDv7 упорядочен по времени, поэтому вставки ложатся в конец индекса и не
фрагментируют B-дерево, как случайный UUIDv4. При этом id можно сгенерировать до записи
в базу, что упрощает код, и он не раскрывает, сколько у нас турниров и игроков — в отличие
от автоинкремента, который будет светиться в ссылках вида `/tournaments/3`.

**Чем платим.** 16 байт против 8 у bigint и менее приятные id в логах. На наших объёмах
несущественно.

## Р-008 · Тесты идут на SQLite локально и на Postgres в CI

**Дата:** 2026-08-08 · **Веха:** M2

Локальный прогон — SQLite в памяти, ноль настройки. В CI поднимается настоящий Postgres
сервис-контейнером, и тот же набор тестов идёт по нему.

**Почему.** Локальные тесты должны быть мгновенными и не требовать docker, иначе их
перестают запускать. Но SQLite не Postgres: он иначе относится к типам, к
конкурентности и к части ограничений. Гонять полный набор на настоящем Postgres в CI —
дешёвая страховка от «на моей машине работало».

**Чем платим.** Модели придётся держать переносимыми: никаких Postgres-специфичных типов
там, где без них можно обойтись. Если позже понадобится `JSONB` или массивы — SQLite-ветку
тестов придётся сузить, и это будет отдельным решением.

## Р-007 · HTTP API переезжает из M2 в M4

**Дата:** 2026-08-08 · **Веха:** M2 → M4

Изначально M2 значилась как «персистентность + API». API откладывается до M4, где появляется
веб — его первый настоящий потребитель.

**Почему.** Проектировать эндпоинты, которые никто не вызывает, — это гадание. Бот (M3)
прекрасно обходится без HTTP: он работает с тем же слоем сценариев в одном процессе
(см. [Р-006](#р-006--бот-работает-со-слоем-сценариев-напрямую-а-не-через-http)). Когда
появится веб, форма API будет продиктована реальными экранами.

**Что это меняет для M2.** Веха становится «персистентность + слой сценариев», и её
результат виден руками: турнир можно провести в CLI, выйти, вернуться и продолжить с того
же места. Это лучший показатель того, что персистентность работает, чем набор
непроверяемых эндпоинтов.

**Чем платим.** Ничем существенным: бизнес-логика всё равно живёт в слое сценариев, а API
будет тонким транспортом над ним.

## Р-006 · Бот работает со слоем сценариев напрямую, а не через HTTP

**Дата:** 2026-08-08 · **Веха:** M3

Telegram-бот импортирует слой сценариев и ходит в базу в своём процессе. Он не будет
HTTP-клиентом собственного API.

**Почему.** Это инструмент для одной группы, а не распределённая система. Сетевой прыжок
внутрь самого себя добавил бы задержку, второй источник ошибок и необходимость держать
API живым ради бота. Граница, которая действительно важна, — между сценариями и
хранилищем, а не между процессами.

**Чем платим.** Бот и API будут двумя процессами, пишущими в одну базу. Для Postgres это
норма. Если когда-нибудь понадобится развести их по разным машинам с разными правами —
решение придётся пересмотреть.

## Р-002 · Правила ruff: TRY003 и S311 отключены осознанно

**Дата:** 2026-08-08 · **Веха:** M1

**TRY003** требует убирать тексты ошибок в тела классов исключений. Наши сообщения
контекстные — называют раунд, корт, конкретный неверный счёт — и попадают прямо на глаза
человеку. Шаблонизация сделала бы их хуже.

**S311** ругается на `random.Random`. Воспроизводимость жеребьёвки от сохранённого seed —
это весь смысл движка, криптостойкий генератор её сломает. Отключено точечно, только для
движка и CLI: всё по-настоящему секретное появится в других файлах и останется под
проверкой.

## Р-001 · Разницы очков нет в каскаде тай-брейков

**Дата:** 2026-08-06 · **Веха:** M1

**Почему.** Матч всегда идёт до фиксированной суммы, поэтому
`разница = 2 × набрано − цель × сыграно`. При равном числе сыгранных матчей равенство
очков автоматически означает равенство разницы — как ступень каскада она не может
сработать никогда. Обнаружено при реализации, изначально в спеке она была.

**Что осталось.** Поле `diff` в таблице живёт: оно хорошо читается. Когда появятся byes
и число сыгранных матчей начнёт различаться, правильным критерием станет среднее за матч,
а не разница.
