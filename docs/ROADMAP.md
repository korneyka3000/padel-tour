# Дорожная карта

Живой документ. Здесь лежат все фичи из исходной идеи, разбитые на вехи так, чтобы каждая
веха заканчивалась чем-то, чем можно пользоваться. Ничего не теряется: то, что решили не
делать сейчас, уезжает в бэклог внизу с пометкой почему.

## Как мы работаем

Каждая веха проходит цикл **спек → план → реализация**. Спек ложится в
`docs/superpowers/specs/`, план обсуждается до кода. Веха считается готовой, когда зелены
`pytest`, `ruff`, `ty` и `prek run --all-files`, а результат прогнан руками.

Сквозные правила:

- **Движок не знает ни о чём, кроме правил.** Ни БД, ни HTTP, ни Telegram. Всё остальное
  импортирует движок, но не наоборот.
- **Реализация на английском** — код, докстринги, сообщения об ошибках. Документы и
  интерфейс для людей — на русском.
- **Игрок ≠ аккаунт.** Игрок заводится по имени и сразу играет. Аккаунт нужен только чтобы
  человек сам видел свою статистику, и прикрепляется позже.

## M1 — Движок турниров ✅

Чистая Python-библиотека, ноль зависимостей.

- Americano: полный цикл n−1 раундов на Z-циклической whist-схеме, reroll пересадкой
- Mexicano: пошаговая генерация по таблице, три схемы пар (crossover / split / top-heavy)
- Счёт points-to-N, запись и правка результата, досрочное завершение
- Таблица с детерминированным каскадом тай-брейков
- `progression()` — данные для графика «матч за матчем»
- CLI на typer для ручного прогона

Спек: [`specs/2026-08-06-tournament-engine-design.md`](superpowers/specs/2026-08-06-tournament-engine-design.md)

## M2 — Персистентность и слой сценариев ✅

**Зачем:** турнир должен переживать перезапуск, а истории турниров — накапливаться. Без
этого ни бот, ни веб невозможны.

**Результат вехи:** турнир можно провести в CLI, выйти, вернуться и продолжить с того же
места. HTTP API сюда не входит — он переехал в M4, к своему первому потребителю
(см. [Р-007](DECISIONS.md)).

**Сущности**

| Модель | Содержание |
|---|---|
| `Group` | сообщество: имя, опциональный `telegram_chat_id` |
| `Player` | имя в группе. Без аккаунта. Это то, что видно в списках участников |
| `Tournament` | группа, формат, очки за матч, схема пар, план раундов, seed, статус |
| `TournamentPlayer` | состав турнира + позиция жеребьёвки (последний тай-брейк) |
| `Round` / `Match` | раунды и матчи со счётом — нормализованно, чтобы по ним считалась статистика |

Раунды и матчи хранятся явно, а не выводятся из seed: в Mexicano они зависят от результатов,
а правка счёта не должна переписывать уже сыгранное. Модуль-маппер собирает из строк БД
`TournamentState`, движок считает, результат сохраняется обратно.

**Слой сценариев**

Одна точка входа для всех интерфейсов — бот, будущий API и CLI зовут одно и то же:

- группы и игроки: создание, список, переименование
- турнир: создание из состава, reroll, следующий раунд, завершение
- результат: запись и правка по `(round, court)`
- чтение: таблица, progression, история турниров группы, профиль игрока

**Стек:** SQLAlchemy 2.0 (async), Alembic, asyncpg. Локально SQLite, в CI и деплое Postgres.

**Готово, когда:** турнир проводится в CLI, переживает перезапуск и продолжается с того же
раунда; история прошлых турниров видна.

## M3 — Telegram-бот ✅

**Зачем:** это то, чем реально пользуются на корте. Первый интерфейс, который увидят люди.

- Бот добавляется в чат группы, `/start` привязывает `Group` к `chat_id`
- Управление ростером: добавить игрока по имени, переименовать, скрыть ушедшего
- Сбор состава на турнир: инлайн-клавиатура с галочками по игрокам группы
- Настройка турнира: формат, очки за матч, схема пар, число раундов
- Показ раунда и ввод счёта инлайн-кнопками
- Таблица, график хода турнира, история турниров, личная статистика

**Ключевое требование: бот не спамит.** На турнир заводится ровно одно сообщение; его
`chat_id` и `message_id` хранятся в `Tournament`, и каждое действие делает
`edit_message_text`, а не новое сообщение. Экраны (раунд / таблица / график / история)
переключаются кнопками в том же сообщении.

**Ввод счёта.** Клавиатура «все варианты счёта» для матча до 24 — это 25 кнопок, слишком
много. Двухшаговый ввод: сначала кнопка победившей пары, потом её счёт из компактной сетки
(13–24), второй счёт выводится. Один тап на типовой матч.

**Стек:** aiogram 3, для начала polling. Бот зовёт слой сценариев из M2 напрямую, в своём
процессе, без HTTP (см. [Р-006](DECISIONS.md)).

**Готово, когда:** турнир на 8 человек проводится с телефона от жеребьёвки до итоговой
таблицы, и в чате при этом одно-единственное сообщение.

## M4 — HTTP API и веб со статистикой

**Зачем:** бот хорош на корте, но разбирать статистику удобнее на большом экране.

Сюда же переехал **HTTP API** — тонкий транспорт поверх слоя сценариев из M2. Его форму
диктуют реальные экраны, поэтому он строится здесь, а не заранее.

Фронтенд живёт в этом же репозитории, в `web/` (см. [Р-010](DECISIONS.md)).

- Живая страница турнира: текущий раунд, таблица, график
- **График «матч за матчем»** — накопленные очки и движение по местам, по игроку линия.
  Данные уже отдаёт `progression()`
- Архив турниров группы
- Статистика группы: кто с кем чаще выигрывает, распределение мест, активность
- Личный профиль: история, средние очки за матч, лучшие и худшие партнёры
- Доступ на чтение по ссылке-токену группы — полноценный вход появится в M5

**Стек:** FastAPI на бэкенде; React + Vite + TypeScript и Recharts во фронтенде. На этой
вехе подключается skill `frontend-design`.

**Готово, когда:** по ссылке видно живой турнир и архив, график читается с телефона.

## M5 — Аккаунты и права

**Зачем:** веб — витрина, потому что не знает, кто перед ним. Это ворота, за которыми стоят
остальные вехи.

- `Account` — наша личность; `Identity(provider, external_id)` — как в неё входят
- Вход по magic link на почту; пароля нет
- Приглашение на конкретного игрока: одно, принять можно из браузера или из Telegram
- Владелец группы и организатор турнира; счёт вводит организатор либо игравшие
- Группы становятся закрытыми, страница турнира остаётся открытой по ссылке

Попутно чинится изъян M3: `organiser_telegram_id` и `telegram_chat_id` — телеграм-образные
поля внутри домена. Уезжают в связки.

Спек: [`specs/2026-08-09-accounts-design.md`](superpowers/specs/2026-08-09-accounts-design.md)

**Сделано.** Вход, приглашения, права и закрытые группы работают. Заодно въехало то, без
чего вход упирался в пустую страницу: завести группу и вести ростер из браузера.

**Готово, когда:** ✅ ссылка из письма пускает внутрь, приглашение делает человека игроком
и из браузера, и из чата, чужая группа отвечает 403, страница турнира открыта по ссылке.

## M6 — Веб ведёт турнир ✅

**Зачем:** то, из-за чего было ощущение витрины. Теперь человек без Telegram — полноценный
участник, а не зритель.

- Сбор состава, настройка и жеребьёвка в вебе
- Ввод счёта с телефона, правка ошибочного — с переходом по сыгранным раундам
- Переименовать игрока, убрать из ростера

Счёт пишется одним `PUT`: телефон вводит то, что говорит табло, а первый это ввод или
исправление — факт о сохранённом состоянии, и его читает сервер. Каждая запись отвечает
целым турниром, потому что счёт двигает и таблицу, и график, и — в Mexicano — следующий
раунд. Страница получает блок `viewer` вместо готового вердикта: правило «кому можно вносить
счёт» остаётся одно, а не две расходящиеся копии.

Спек: [`specs/2026-08-09-web-runs-a-tournament.md`](superpowers/specs/2026-08-09-web-runs-a-tournament.md)

**Готово, когда:** ✅ турнир на восемь человек проводится целиком из браузера, ошибочный счёт
правится, игрок переименовывается и убирается, чужой турнир открыт по ссылке без единой кнопки.

## M6.5 — Долги и языки ✅

Накопилось из разговора по ходу M6, ничего из этого не блокировало веху.

- **`pydantic-settings` вместо `python-dotenv`.** Один типизированный объект вместо десяти
  `os.environ.get` в шести модулях. Кеша нет — замер показал 111 мкс на построение против
  одного-трёх вызовов на запрос, а кеш ломал четыре теста. `.env` в тестах не читается:
  в копии разработчика живой токен и строка подключения к проду
- **У ошибки есть машинный код**, выведенный из имени класса, и параметры рядом с текстом,
  а не внутри него. Сообщения — английские, как и всё в `src`. `ForbiddenError` разошёлся
  на четыре подкласса: одного кода на «вы не в группе» и «вы не играли этот матч» мало
- **Языки на фронте** — словарь без библиотеки, `en` типизирован по ключам `ru`, так что
  забытая фраза не собирается. Числительные и даты через `Intl`
- **График в боте — настоящий PNG**, места по раундам, плюс кнопка «Открыть в вебе».
  Рисуется Pillow: бот в проде живёт в той же serverless-функции, что API, и matplotlib
  туда не поедет

Спек: [`specs/2026-08-10-settings-language-and-a-real-chart.md`](superpowers/specs/2026-08-10-settings-language-and-a-real-chart.md)

## M7 — Подтверждение результатов

**Зачем:** защита от недобросовестного счёта, когда группа перерастает круг друзей.

Подтверждение **необязательное**: счёт засчитывается сразу, соперник может подтвердить или
оспорить. Молчание — согласие, никто никого не ждёт. Оспоренный матч помечается, и решает
организатор правкой счёта — новых механик не нужно.

## Бэклог

Отложено сознательно. Строка живёт здесь, пока не станет вехой.

**Форматы**

- Team Americano / Team Mexicano — фиксированные пары, меняются только соперники
- Mixicano — ограничение «в паре мужчина и женщина»
- King of the Court — победители остаются на корте
- Winner's Court, Pyramid, Box League

**Движок**

- **Byes** — составы не кратные 4. Требует ранжирования по среднему за матч вместо суммы,
  и гарантии, что все пропускают одинаково. Самое востребованное из бэклога
- Анти-повтор в Mexicano: если 1+4 уже играли вместе, брать следующую схему. Сейчас на
  длинном турнире с устоявшейся таблицей пары начинают повторяться
- Дропаут и дозаявка по ходу турнира
- Americano произвольной длины: не n−1, а сколько влезло по времени, с best-effort
  расписанием
- Меньше кортов, чем n/4: расписание то же, матчи последовательно, плюс оценка времени

**Статистика**

- Сквозной рейтинг между турнирами (Elo / Glicko)
- Химия пар: с кем выигрываешь чаще ожидаемого
- Экспорт в CSV и PDF

**Прочее**

- i18n интерфейса (русский и английский)
- Уведомления: напоминание о турнире, итоги в чат
