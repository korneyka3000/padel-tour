# Движок падел-турниров — дизайн

Дата: 2026-08-06
Статус: согласован
Веха: M1 из пяти

## Задача

Приложение для генерации падел-турниров и статистики: Americano/Mexicano, участники,
Telegram-бот, веб с личной и групповой статистикой, графики «матч за матчем».

Это пять независимых подсистем. Первой строится **ядро — движок турниров**: чистая
Python-библиотека без БД, HTTP и UI. Всё остальное насаживается на неё как на единственный
источник истины о правилах.

## Форматы: что говорит предметная область

**Americano** — расписание известно заранее, каждый партнёрит с каждым. Формально это
*whist tournament design* Wh(n): существует для всех n ≡ 0 mod 4; за n−1 раундов каждая
пара игроков партнёрит ровно 1 раз и встречается соперниками ровно 2 раза.

**Mexicano** — раунд 1 случайный, дальше четвёрки нарезаются по текущей таблице.
Стандартная схема на корте — 1+4 vs 2+3 («crossover»); в ходу также 1+3 vs 2+4 («split»)
и 1+2 vs 3+4 («top-heavy»). Официального правила нет ни у одной федерации.

**Счёт** — матч до фиксированной суммы очков (16 / 21 / 24 / 32; ходовой 24). Каждый игрок
получает счёт своей команды в личную копилку: 14:10 → +14 обоим победителям, +10 обоим
проигравшим.

Источники: [americano-padel.app](https://americano-padel.app/en/blog/mexicano-padel-rules-format-guide/),
[hostatourney.com](https://hostatourney.com/en/blog/americano-padel-rules-schedule),
[padeli.com](https://padeli.com/get-started/formats/),
[Social golfer problem](https://en.wikipedia.org/wiki/Social_golfer_problem).

## Архитектура

Неизменяемые dataclass-ы и свободные функции `state -> state`. Ни ввода-вывода, ни
глобального `random`, ни внешних зависимостей. Игроки для движка — непрозрачные
`PlayerId: str`; имена и аккаунты живут выше, в M2.

Детерминизм жёсткий: `seed: int` хранится в состоянии, вся случайность идёт через
`random.Random(seed)`. Одинаковый seed даёт одинаковое расписание. Это требование не
косметическое: в Mexicano ранг определяет пары следующего раунда, поэтому ранжирование
обязано быть воспроизводимым.

`standings.py` и не считает очки сам.

### Генерация Americano: Z-циклическая whist-схема

Вместо таблицы на каждое n хранится один **стартер** — первый раунд над `Z_{n-1} ∪ {∞}`.
Остальные n−2 раунда получаются прибавлением 1 по модулю n−1 ко всем конечным элементам
(∞ неподвижна).

Стартер корректен тогда и только тогда, когда:

1. использует каждый элемент `Z_{n-1} ∪ {∞}` ровно один раз;
2. разности конечных партнёрских пар покрывают каждый из (n−2)/2 классов разностей
   ровно один раз;
3. разности конечных соперничающих пар покрывают каждый класс ровно два раза.

Пары с участием ∞ выполняются автоматически: ∞ партнёрит с `a+j` по всем j (каждая пара
ровно раз) и соперничает с `c+j`, `d+j` (каждая пара ровно дважды).

Пример для n=8 над `Z_7 ∪ {∞}`: стартер `(∞,0 | 1,3)`, `(2,6 | 4,5)`.
Партнёрские разности 2, 3, 1 — все три класса по разу. Соперничающие разности
1, 3, 2, 3, 2, 1 — каждый класс дважды.

`search_starter(n)` — перебор с отсечениями — находит стартеры офлайн; найденные значения
захардкожены в `STARTERS` и проверяются тестами. Это защита от опечаток в значениях из
литературы: если валидатор падает, стартер пересчитывается поиском.

### Публичный API

```python
create_americano(players, config, seed) -> TournamentState   # всё расписание сразу
create_mexicano(players, config, seed)  -> TournamentState   # только раунд 1
reroll(state) -> TournamentState                             # пока нет результатов
record_result(state, round_no, court, score_a, score_b) -> TournamentState
next_round(state) -> TournamentState                         # Mexicano
finish(state) -> TournamentState                             # досрочно допустимо
standings(state) -> tuple[StandingRow, ...]
progression(state) -> Mapping[PlayerId, tuple[ProgressPoint, ...]]
```

`TournamentConfig`: `format`, `points_per_match` (16/21/24/32), `pairing_pattern`
(Mexicano), `rounds` (Mexicano — задаёт организатор; Americano — всегда n−1).

`reroll` для Americano — новая случайная биекция «игрок → слот схемы». Сама схема
математически идеальна и не может стать хуже: меняются только конкретные пары и порядок.
Для Mexicano — перетасовка раунда 1. После первого записанного результата reroll запрещён.

`finish` разрешён на любом раунде: 11 раундов на 12 человек — это ~2.5 часа, и группе
нужна возможность остановиться раньше без порчи таблицы.

### Каскад тай-брейков

1. сумма набранных очков
2. число побед
3. очная встреча — сумма очков, взятых у остальных участников той же группы равных
4. порядок жеребьёвки — перестановка, зафиксированная при создании через `Random(seed)`

Ступень 4 обязательна: она гарантирует полный порядок всегда, без неё Mexicano
недетерминирован.

**Разницы очков в каскаде нет намеренно.** Матч всегда идёт до фиксированной суммы, поэтому
`разница = 2 × набрано − цель × сыграно`: при равном числе сыгранных матчей равенство очков
автоматически означает равенство разницы. Как ступень каскада она не может сработать никогда.
В `StandingRow` разница остаётся как поле — она хорошо читается в таблице. Когда в v2
появятся byes и число сыгранных матчей начнёт различаться, правильным критерием будет
среднее за матч, а не разница.

### Данные для графика

`progression(state)` даёт по игроку последовательность
`(round_no, points_in_round, cumulative_points, rank_after_round)` — ровно то, что нужно
для графика «матч за матчем». Живёт в ядре, чтобы бот и веб считали одно и то же.

### Ошибки

`PadelEngineError` и наследники: `InvalidPlayerCount` (с подсказкой «нужно 8, 12 или 16 —
сейчас 9»), `UnsupportedPlayerCount`, `DuplicatePlayer`, `RoundIncomplete`,
`ResultAlreadyRecorded`, `CannotRerollAfterStart`, `TournamentFinished`, `InvalidScore`,
`UnknownMatch`, `WrongFormat`.

### Корты

Число кортов = n/4 — это параллелизм внутри раунда, а не параметр алгоритма. Если кортов
физически меньше, матчи раунда играются последовательно; расписание не меняется.
