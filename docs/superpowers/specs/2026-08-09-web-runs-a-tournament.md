# M6 — Веб ведёт турнир

**Дата:** 2026-08-09 · **Статус:** в работе

## Зачем

После M5 в браузер можно войти, завести группу и добавить людей в ростер — и на этом всё
кончается. Турнир по-прежнему проводится только из Telegram. Для человека без Telegram —
а это исходное ограничение всей затеи, бот в России недоступен, — веб остаётся витриной:
видно чужую игру, поучаствовать нельзя.

Веха закрывает разрыв. После неё оба интерфейса умеют одно и то же, и ни один из них не
обязателен.

## Что входит

1. Сбор состава, настройка и жеребьёвка турнира в браузере
2. Ввод счёта с телефона и правка ошибочного
3. Переименовать игрока, убрать из ростера

## Что не входит

Подтверждение результата соперником (M7), живое обновление страницы без перезагрузки (M8),
переводы интерфейса и переезд конфигурации на `pydantic-settings` (M6.5).

---

## Опорная точка

Слой сценариев уже умеет всё, что нужно, и уже проверяет права. `start_tournament`,
`reroll_tournament`, `record_score`, `amend_score`, `advance_round`, `finish_tournament`,
`rename_player`, `deactivate_player` — каждая берёт `actor` и зовёт нужный `require_*`.
Бот ходит в них напрямую, минуя HTTP, и это не меняется.

Значит веха — это **транспорт и экраны**, а не новая логика. Ни одного нового правила в
`services/` не появляется. Если по ходу выяснится, что правило нужно, — оно пишется в
`permissions.py` и достаётся обоим интерфейсам сразу, а не в роутере.

---

## Решение 1 · Счёт пишется одним `PUT`, а не двумя разными глаголами

В сервисах два вызова: `record_score` для первого раза и `amend_score` для правки. Первый
падает `ResultAlreadyRecordedError`, если счёт уже есть, — и это правильная защита от
случайного повторного нажатия в боте, где кнопка одна.

Наружу они выходят одним эндпоинтом:

```
PUT /api/tournaments/{id}/rounds/{round_no}/courts/{court}
{ "score_a": 17, "score_b": 7 }
```

Телефону всё равно, первый это ввод или исправление; он знает только «на этом корте было
столько». Роутер смотрит, есть ли уже счёт, и зовёт нужную функцию. `PUT` честно описывает
семантику: состояние матча становится таким, каким его прислали, сколько раз ни повтори.

Цена: клиент теряет защиту от двойного нажатия, которая есть у бота. Она ему и не нужна —
экран показывает текущий счёт, и второе нажатие с тем же значением ничего не меняет.

## Решение 2 · Страница турнира сама говорит, что вам можно

`require_can_score` — правило с четырьмя ветками: организатор может всё; если организатора
нет, может любой участник; если аккаунт не привязан ни к одному игроку турнира, тоже может
(до принятия приглашения мы не отличаем игрока от зрителя); а вот привязанный игрок может
только свои корты.

Клиент обязан показывать те же кнопки, что сервер пропустит, иначе половина кнопок отвечает
403. Повторять это правило в TypeScript — значит завести вторую копию, которая разойдётся
с первой при первом же изменении. Поэтому сервер отдаёт исходные данные, а не готовый ответ:

```jsonc
"viewer": {
  "is_member": true,
  "is_organiser": false,
  "plays_as": "0198…",      // игрок, которым вы играете в этом турнире, или null
  "anyone_may_score": false // у турнира нет организатора
}
```

и в каждом матче появляются `team_a_ids` / `team_b_ids`, потому что сейчас матч несёт только
имена, а сравнивать надо по идентификаторам — тёзки в ростере законны.

Правило на клиенте становится одной функцией в `lib/`, читаемой рядом с серверной.

Альтернатива — считать на сервере `can_score: bool` для каждого матча — отвергнута: это
`n` булевых полей вместо четырёх, и они устаревают на клиенте после каждого хода, тогда как
`viewer` неизменен на всё время турнира.

## Решение 3 · Убрать игрока — значит скрыть, а не удалить

`deactivate_player` уже так и делает: ставит `is_active = false`. Удаление строки снесло бы
его матчи и переписало историю группы. В интерфейсе это «Убрать из состава»: игрок исчезает
из списка для новых турниров, но остаётся в прошлых таблицах и в своём профиле.

Возврата в состав в этой вехе нет — не встречалось нужды; строка уезжает в бэклог.

## API

Всё под `/api`, всё требует аккаунта, кроме уже существующего чтения турнира по ссылке.

| Метод | Путь | Кто | Ответ |
|---|---|---|---|
| `POST` | `/groups/{id}/tournaments` | участник | `201 Tournament` |
| `POST` | `/tournaments/{id}/reroll` | организатор | `Tournament` |
| `PUT` | `/tournaments/{id}/rounds/{n}/courts/{c}` | игравшие или организатор | `Tournament` |
| `POST` | `/tournaments/{id}/next-round` | участник | `Tournament` |
| `POST` | `/tournaments/{id}/finish` | организатор | `Tournament` |
| `PATCH` | `/players/{id}` | владелец группы | `Player` |
| `DELETE` | `/players/{id}` | владелец группы | `204` |

Каждый пишущий эндпоинт отвечает **целым турниром**, а не фрагментом. Счёт меняет таблицу,
график и — в Mexicano — состав следующего раунда; отдавать один матч значит заставить клиент
делать второй запрос за тем, что сервер только что посчитал.

Тело создания турнира:

```jsonc
{
  "player_ids": ["…", "…"],        // порядок неважен, движок перетасует по seed
  "format": "americano",
  "points_per_match": 24,
  "pairing_pattern": "crossover",  // только для mexicano
  "rounds": 7                      // только для mexicano
}
```

Валидация состава остаётся в движке: он один знает, что Americano бывает только на кратном
четырём, и умеет сказать это словами.

## Экраны

**Группа** (`/groups/:id`) — ростер получает правку: переименование по месту и «убрать».
Кнопки видны только владельцу, `is_owner` уже приходит. Плюс кнопка «Собрать турнир», если
активного нет, и «Идёт турнир →», если есть.

**Сбор** (`/groups/:id/play`) — галочки по ростеру со счётчиком и подсказкой о допустимых
числах, выбор формата, очков, схемы пар и числа раундов. Кнопка жеребьёвки неактивна, пока
состав не подходит под формат. После жеребьёвки — переход на турнир.

**Турнир** (`/tournaments/:id`) — уже показывает раунды, таблицу и график. Добавляется ввод:
на каждом корте, где счёта нет и вам можно, два поля и кнопка; там, где счёт есть, — он сам
и «исправить». Организатору сверху «Пересдать» (пока нет результатов) и «Завершить».
Anonymous и не-участник видят страницу как раньше, без единой кнопки.

Ввод счёта — два числа, потому что на вебе клавиатура есть, а двухшаговая сетка бота нужна
была из-за отсутствия ввода. Сумма проверяется на клиенте до отправки, чтобы ошибка нашлась
раньше сети, и на сервере движком, потому что клиент не барьер.

## Готово, когда

Турнир на восемь человек проводится целиком из браузера с телефона: состав, жеребьёвка,
счёт за каждый матч, правка ошибочного, следующий раунд в Mexicano, завершение. Игрока можно
переименовать и убрать. Чужой турнир открывается по ссылке и не показывает ни одной кнопки.
Прогон зелёный на SQLite и на Postgres.
