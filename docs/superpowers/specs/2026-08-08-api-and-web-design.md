# M4 — HTTP API и веб

Дата: 2026-08-08
Статус: согласован
Предыдущая веха: [Telegram-бот](2026-08-08-telegram-bot-design.md)

## Задача

Бот хорош на корте: два тапа, одно сообщение, ничего лишнего. Но разбирать статистику в
чате неудобно — там нет места для графика на восемь линий и для архива за полгода.

M4 добавляет два слоя: **HTTP API** — тонкий транспорт поверх слоя сценариев из M2 — и
**веб** поверх него. Форму API диктуют реальные экраны, поэтому он строится здесь, а не
заранее ([Р-007](../../DECISIONS.md)).

Всё едет на Vercel ([Р-016](../../DECISIONS.md)), включая бота, и из этого следует его
переезд на webhook.

## Раскладка репозитория

Фронтенд живёт здесь же ([Р-010](../../DECISIONS.md)):

```
src/padel_tour/api/     FastAPI: роутеры, схемы, зависимости
web/                    React + Vite + TypeScript
api/index.py            точка входа Vercel — импортирует приложение
vercel.json             сборка, маршруты, регион
```

`api/index.py` — три строки. Vercel ищет точку входа именно там; сам код живёт в пакете,
где его видят тесты и линтеры.

## Что отдаёт API

Эндпоинты выведены из экранов, а не из таблиц. Всё только на чтение, кроме вебхука: писать
в M4 можно по-прежнему из бота и CLI, а публичная запись без аутентификации была бы дырой.
Запись из веба появится в M5 вместе с аккаунтами.

| Метод | Путь | Зачем |
|---|---|---|
| `GET` | `/api/health` | жив ли сервис и доступна ли база |
| `GET` | `/api/groups` | список групп |
| `GET` | `/api/groups/{id}` | группа с составом |
| `GET` | `/api/groups/{id}/tournaments` | архив, с постраничностью |
| `GET` | `/api/groups/{id}/active` | идущий турнир, или `204` |
| `GET` | `/api/tournaments/{id}` | турнир целиком: раунды, таблица, progression |
| `GET` | `/api/players/{id}` | профиль: история и сводка |
| `POST` | `/api/telegram/webhook` | приём апдейтов от Telegram |

Ответы — Pydantic-схемы, отдельные от `views` слоя сценариев. Разделение не ради
церемонии: `TournamentView` таскает внутри `TournamentState` для вызывающих, которым нужен
движок, а в JSON это лишнее. Схема API — то, что реально уходит клиенту, и её можно менять
независимо.

### Ошибки

`ServiceError` и ошибки движка мапятся на статусы одним обработчиком: `NotFoundError` → 404,
`ConflictError` → 409, остальное из наших иерархий → 400. Текст отдаётся как есть — он
написан для человека. Всё прочее — 500 без подробностей наружу.

## Веб

Три страницы, читаемые с телефона: смотреть их будут по дороге домой с корта.

| Страница | Что на ней |
|---|---|
| `/g/{group}` | идущий турнир, если есть; иначе архив |
| `/t/{tournament}` | раунды, таблица, **график «матч за матчем»** |
| `/p/{player}` | профиль: сколько турниров, среднее за матч, распределение мест |

**График** — главное, ради чего затевался веб: накопленные очки по раундам, линия на
игрока, плюс движение по местам. Данные уже отдаёт `progression()` из M1 — считать на
клиенте ничего не нужно.

**Доступ** — по ссылке. Ссылка на группу знает `id`, этого достаточно, чтобы посмотреть.
Полноценный вход появится в M5; до тех пор ссылка и есть ключ, и это записано честно,
а не выдаётся за защиту.

**Стек:** React 19, Vite, TypeScript, Recharts. Тёмная тема по системной настройке —
падел вечерний, и телефон в это время обычно в тёмной.

На этом этапе подключается skill `frontend-design`: дизайн должен быть осознанным, а не
набором дефолтов.

## Бот: polling → webhook

Serverless-функция не держит долгоживущий процесс, поэтому polling на Vercel невозможен.
Webhook ложится ровно: это обычный POST-эндпоинт.

- `POST /api/telegram/webhook` принимает апдейт, отдаёт его диспетчеру aiogram.
- Заголовок `X-Telegram-Bot-Api-Secret-Token` сверяется с `TELEGRAM_WEBHOOK_SECRET`.
  Без этого эндпоинт может дёрнуть кто угодно.
- Адрес регистрируется один раз командой `padel-tour-bot set-webhook`.
- **Polling остаётся** для локальной разработки: `padel-tour-bot poll`. Гонять ngrok ради
  проверки одной кнопки — лишняя работа.

Хендлеры не меняются вообще: они уже написаны против диспетчера, а не против транспорта.

## Соединения с базой

Fluid compute переиспользует «тёплые» инстансы, поэтому обычный пул SQLAlchemy безопасен и
является рекомендуемым способом — при условии, что берётся **пулевая** строка Neon (с
`-pooler`). Наша именно такая.

Движок создаётся один раз на инстанс, а не на запрос: пул, который живёт один запрос, — это
просто медленный способ не иметь пула.

## Тестирование

- **API** — через `httpx.ASGITransport`, без поднятия сервера: список, детали, 404 на
  несуществующий id, 409 на конфликт.
- **Схемы** — что ответ турнира содержит и таблицу, и progression, и что имена не потеряны.
- **Вебхук** — что без правильного секрета приходит 401, а с ним апдейт доезжает до
  хендлера.
- **Фронтенд** — Vitest на разбор ответов и на формирование данных графика; сама вёрстка
  проверяется глазами.

## Верификация

- `pytest`, `ruff`, `ty` — чисто; фронт: `tsc --noEmit`, `vitest`, `eslint`.
- Локально: `uvicorn` поднимает API, `vite dev` — фронт; турнир, созданный ботом, виден
  на странице, график рисуется.
- На Vercel: превью-деплой открывается, `/api/health` отвечает, страница турнира грузится
  с настоящей Neon.
- Бот: после `set-webhook` кнопки в чате работают так же, как на polling.
