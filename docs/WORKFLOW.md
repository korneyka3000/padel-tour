# Как мы ведём работу

Одна фича за раз, от идеи до зелёного CI. Документ описывает цикл и роли — что делаю я,
что нужно от тебя.

## Цикл одной фичи

```
1. Разбор     →  2. Спек     →  3. План     →  4. Реализация  →  5. Приёмка
   вопросы        документ      шаги+файлы     TDD + коммиты      ручной прогон
```

**1. Разбор.** Беру следующую фичу из [`ROADMAP.md`](ROADMAP.md), задаю вопросы там, где
разные ответы ведут к разному коду. Развилки, которые можно решить разумным умолчанием,
решаю сам и говорю об этом — не спрашиваю.

**2. Спек.** Согласованное решение ложится в `docs/superpowers/specs/YYYY-MM-DD-<тема>.md`:
зачем, что решили, архитектура, что осталось за бортом. Спек — это то, к чему потом
апеллируем, когда «а почему так».

**3. План.** Пошаговый план: какие файлы, в каком порядке, что переиспользуем.
Ты его утверждаешь до кода.

**4. Реализация.** Тесты идут вместе с кодом, не после. Коммиты осмысленные, по логическим
кускам, а не «фикс», «ещё фикс». Каждый коммит проходит хуки.

**5. Приёмка.** Прогон руками по сценариям из спека, отчёт: что работает, что осталось,
где я отступил от плана и почему.

## Ветки и коммиты

Фича живёт в ветке `feat/<короткое-имя>`, вливается в `main` через PR. `main` всегда
зелёный. CI гоняет ruff, ruff format, ty и pytest на каждый push и PR.

Локально то же самое ловит `prek`. Ставится один раз:

```bash
uv run prek install --hook-type pre-commit --hook-type pre-push
```

На коммите — быстрые проверки изменённых файлов. **На push — ровно то, что гоняет CI**:
ruff, format и ty по всему дереву и без кеша. Это не перестраховка: оба падения CI, что уже
были, коммитный хук увидеть не мог — один прятался за устаревшим кешем ruff, второй ломался
только на Postgres.

Если работа трогает базу, перед пушем стоит прогнать набор ещё и на настоящем Postgres,
а не только на SQLite ([Р-013](DECISIONS.md)):

```bash
docker run -d --name padel-pg -e POSTGRES_USER=padel -e POSTGRES_PASSWORD=padel \
  -e POSTGRES_DB=padel_test -p 55432:5432 postgres:18-alpine
TEST_DATABASE_URL='postgresql://padel:padel@localhost:55432/padel_test' uv run pytest
docker rm -f padel-pg
```

## Что нужно от тебя и когда

Инфраструктура нужна не вся сразу. Список того, что понадобится, и **к какой вехе** —
в [`INFRASTRUCTURE.md`](INFRASTRUCTURE.md). Смысл в том, чтобы ты заводил доступы заранее,
а не в момент, когда работа упирается.

Ближайшее решение за тобой — где держать базу для M2. Всё остальное ждёт своей вехи.

## Правила, которые не обсуждаются заново

- Движок не знает ни про БД, ни про HTTP, ни про Telegram. Зависимости идут в одну сторону.
- Реализация на английском: код, докстринги, сообщения об ошибках. Документы и тексты для
  людей — на русском.
- Игрок ≠ аккаунт. Регистрация никогда не является условием того, чтобы сыграть.
- Детерминизм: всё, что случайно, идёт от сохранённого seed. Турнир воспроизводим.
- Секреты только в переменных окружения. В репозитории — `.env.example` без значений.
